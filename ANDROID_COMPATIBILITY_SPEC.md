# Техническая спецификация совместимости Windows и Android (Arspective GTD)
`ANDROID_COMPATIBILITY_SPEC.md`

Настоящий документ подготовлен на основе глубокого анализа фактической реализации Windows-версии приложения **Arspective GTD** (Electron + React + SQLite). ## 1. Общая архитектура Windows-приложения

### 1.1 Используемые технологии
- **Среда выполнения:** Electron 45.1.0, Node.js v20.
- **Frontend / Renderer:** React 19, TypeScript, Tailwind CSS 3, Vite 8, Lucide React (иконки).
- **Визуальный редактор заметок:** TipTap 3 (`@tiptap/react`, `@tiptap/starter-kit`, `@tiptap/extension-underline`, `@tiptap/extension-link`, `tiptap-markdown`).
- **Локальная СУБД:** SQLite 3 через нативный драйвер `better-sqlite3` с включённым WAL-режимом (`journal_mode = WAL`) и каскадными внешними ключами (`foreign_keys = ON`).
- **Сетевой стек синхронизации:** Встроенный Node.js HTTP-сервер (`http.createServer`) без сторонних фреймворков (Express не используется), модуль `crypto` для SHA-256 и генерации токенов, библиотека `qrcode` для отрисовки DataURL QR-кодов.

### 1.2 Структура проекта и ключевые файлы
- `src/main/index.ts` — главный процесс Electron: создание окна, регистрация IPC, автозапуск `SyncServer`.
- `src/main/sync/syncServer.ts` — реализация HTTP-сервера локальной синхронизации.
- `src/main/ipc/` — обработчики IPC для связи Renderer <-> Main (`tasksIpc.ts`, `projectsIpc.ts`, `syncIpc.ts`, `previewIpc.ts`, `systemIpc.ts`, `processingIpc.ts`).
- `src/preload/index.ts` — мост безопасности ContextBridge (`window.gtdApi`).
- `src/storage/database.ts` — инициализация SQLite, определение пути к файлу базы данных.
- `src/storage/migrations/runner.ts` — версионирование схемы БД (миграции 1, 2, 3) и автоматический snapshot-бэкап (`VACUUM INTO`).
- `src/storage/repositories/` — слой доступа к данным:
  - `taskRepository.ts` — CRUD задач, фильтрация по разделам.
  - `projectRepository.ts` — CRUD проектов, связывание с шагами, мягкое и физическое удаление.
  - `syncRepository.ts` — сопряжение устройств, сессии PIN, применение дельт изменений, разрешение конфликтов, tombstones.
  - `sessionRepository.ts` — состояние мастера пошагового разбора корзины.
- `src/domain/gtd/stateMachine.ts` — чистый конечный автомат переходов алгоритма GTD.
- `src/renderer/src/components/MarkdownEditor/` — компоненты двухрежимного редактора заметок.

### 1.3 Расположение пользовательской информации
- База данных SQLite сохраняется по пути:
  `%APPDATA%\arspective-gtd\gtd.db` (в среде Electron: `app.getPath('userData')/gtd.db`).
  При локальной разработке: `.data/gtd.db`.
- Резервные копии: `%APPDATA%\arspective-gtd\backups\pre-migration-backup-<timestamp>.db` и `manual-backup-<timestamp>.db`.
- Настройки интерфейса (тема `'gtd-theme'`, язык `'gtd-language'`) хранятся в браузере Renderer через `localStorage`.

### 1.4 Запуск сервера синхронизации
- Сервер запускается автоматически в главном процессе Electron при старте программы (`app.whenReady()` в `src/main/index.ts`).
- Принимает соединения на всех сетевых интерфейсах (`0.0.0.0`).
- Порт по умолчанию: `52420` (с автоматическим инкрементом `52421`, `52422`..., если порт занят).

## 2. Полная структура данных (SQLite)

### 2.1 Таблица `tasks` (Задачи и Заметки)
Хранит все пользовательские элементы: входящие мысли, действия, события календаря, делегированные задачи, долгосрочные цели, заметки и удалённые элементы в корзине.

| Поле | Тип SQLite | Nullable | Default | Назначение / Описание |
|---|---|---|---|---|
| `id` | `TEXT` | **NOT NULL** | — | Первичный ключ (Primary Key). Формат: `task_<timestamp>_<rand>` или UUID v4. |
| `title` | `TEXT` | **NOT NULL** | — | Текст задачи или заголовок заметки. |
| `notes` | `TEXT` | NULL | `NULL` | Текст заметки / подробное описание задачи. Хранится **строго в сыром переносимом формате Markdown**. |
| `destination` | `TEXT` | **NOT NULL** | `'inbox'` | Раздел GTD: `'inbox'`, `'next_actions'`, `'calendar'`, `'waiting_for'`, `'someday'`, `'notes'`, `'trash'`. |
| `status` | `TEXT` | **NOT NULL** | `'active'` | Статус выполнения: `'active'`, `'completed'`, `'cancelled'`. |
| `project_id` | `TEXT` | NULL | `NULL` | Внешний ключ: `REFERENCES projects(id) ON DELETE SET NULL`. Привязка к проекту. |
| `project_order` | `INTEGER` | NULL | `0` | Порядковый номер шага внутри проекта (для упорядочивания). |
| `due_date` | `TEXT` | NULL | `NULL` | Срок выполнения задачи: дата в формате `YYYY-MM-DD`. |
| `due_time` | `TEXT` | NULL | `NULL` | Срок выполнения: время в формате `HH:mm`. |
| `scheduled_date`| `TEXT` | NULL | `NULL` | Запланированная дата (для календаря): `YYYY-MM-DD`. |
| `scheduled_time`| `TEXT` | NULL | `NULL` | Запланированное время (для календаря): `HH:mm`. |
| `delegated_to` | `TEXT` | NULL | `NULL` | Имя/контакт человека, которому поручена задача (раздел `waiting_for`). |
| `waiting_for` | `TEXT` | NULL | `NULL` | Чего именно ожидаем от ответственного лица. |
| `check_date` | `TEXT` | NULL | `NULL` | Контрольная дата проверки делегированного поручения: `YYYY-MM-DD`. |
| `created_at` | `TEXT` | **NOT NULL** | — | Дата/время создания в формате ISO 8601 UTC (например, `2026-10-30T17:00:00.000Z`). |
| `updated_at` | `TEXT` | **NOT NULL** | — | Дата/время последнего изменения в формате ISO 8601 UTC. Используется для инкрементальной синхронизации. |
| `completed_at` | `TEXT` | NULL | `NULL` | Дата/время завершения задачи (ISO 8601 UTC). Заполняется при переводе в `status = 'completed'`, сбрасывается в `NULL` при возврате. |
| `deleted_at` | `TEXT` | NULL | `NULL` | Отметка времени мягкого удаления (Soft Delete, ISO 8601 UTC). Заполняется при отправке в «Мусор». |

**Индексы таблицы `tasks`:**
- `idx_tasks_dest_status` ON `tasks(destination, status)`
- `idx_tasks_project` ON `tasks(project_id)`
- `idx_tasks_scheduled` ON `tasks(scheduled_date)`
- `idx_tasks_due` ON `tasks(due_date)`

## 3. Полное техническое описание синхронизации

### 3.1 Локальный сервер
- **Фактический порт:** Сервер запускается на порту `52420` (в исходной первоначальной спецификации упоминался `52498`, но в реальном рабочем коде `src/main/sync/syncServer.ts` константой по умолчанию является `52420` с автоматическим инкрементом при занятости).
- **Сетевой интерфейс:** Сервер слушает `0.0.0.0` (все сетевые интерфейсы).
- **Определение IP-адреса ПК:** Метод `SyncServer.getLocalIpAddress()` перебирает сетевые интерфейсы через `os.networkInterfaces()`, отфильтровывает loopback (`127.0.0.1`), IPv6 и отдаёт первый действующий IPv4-адрес локальной сети (предпочтительно диапазоны `192.168.x.x`, `10.x.x.x`, `172.16-31.x.x`).
- **Сетевые ограничения и Windows Firewall:** При первом запуске Windows запрашивает разрешение для Node.js/Electron на открытие входящего TCP-порта в частных сетях. Если пользователь отклонил запрос, мобильный клиент не сможет достучаться до ПК. В Android-приложении при сетевой ошибке `ConnectException / Timeout` обязательно выводить подсказку: *"Проверьте, что телефон и ПК подключены к одному Wi-Fi, и Брандмауэр Windows не блокирует порт 52420"*.

### 3.2 Подключение нового устройства (Pairing)

#### Создание сессии в Windows:
1. Пользователь в Windows открывает Настройки -> Синхронизация -> «Подключить устройство».
2. Windows вызывает `createPairingSession()`:
   - Генерируется случайный 6-значный PIN: `Math.floor(100000 + Math.random() * 900000).toString()`.
   - Генерируется криптографический секрет: `crypto.randomBytes(24).toString('hex')` (48 символов).
   - В таблицу `sync_pairings` сохраняется запись со сроком жизни `ttlSeconds = 600` (10 минут).
   - Формируется JSON-объект:
     ```json
     {
       "app": "ArspectiveGTD",
       "protocol": 1,
       "ip": "192.168.1.105",
       "port": 52420,
       "pin": "482915",
       "secret": "a1b2c3d4e5f60718293a4b5c6d7e8f90123456789abcdef0"
     }
     ```
   - Данный JSON кодируется в изображение QR-кода.

#### Действия Android:
- **Вариант А (Сканирование QR-кода):** Android считывает QR-код, парсит JSON, получает адрес сервера, порт и отправляет запрос на сопряжение с полем `secretToken`.
- **Вариант Б (Ручной ввод):** Пользователь вручную указывает IP-адрес компьютера, порт и 6-значный `pinCode`.

### 3.3 Спецификация REST API

Все эндпоинты поддерживают CORS (`Access-Control-Allow-Origin: *`). Ответы возвращаются в `application/json; charset=utf-8`.

---

#### 1. Проверка доступности: `GET /api/v1/ping`
- **Назначение:** Быстрая проверка доступности сервера в сети перед началом синхронизации.
- **Авторизация:** Не требуется.
- **Ответ сервера (200 OK):**
```json
{
  "status": "ok",
  "server": "Arspective GTD Sync Server",
  "version": "1.0.0",
  "protocolVersion": 1,
  "serverTime": "2026-10-30T17:30:00.123Z"
}
```

---

#### 2. Сопряжение устройства: `POST /api/v1/pair`
- **Назначение:** Одноразовый обмен PIN-кода или секрета из QR на постоянный Bearer Token авторизации.
- **Авторизация:** Не требуется.
- **Тело запроса (Content-Type: application/json):**
```json
{
  "deviceName": "Google Pixel 8 (Android)",
  "pinCode": "482915",
  "secretToken": "a1b2c3d4e5f60718293a4b5c6d7e8f90123456789abcdef0"
}
```
> Примечание: достаточно передать либо `secretToken` (при сканировании QR), либо `pinCode` (при ручном вводе). Поле `deviceName` опционально (по умолчанию присваивается `"Android Device"`).

- **Ответ при успехе (200 OK):**
```json
{
  "success": true,
  "deviceId": "dev_1730309400000_k9x2pa",
  "deviceName": "Google Pixel 8 (Android)",
  "authToken": "7f8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b",
  "serverName": "Arspective GTD"
}
```
> **ВАЖНО для Android:** Полученный `authToken` (64-символьная hex-строка, 32 байта криптографической случайности) необходимо сохранить в постоянную защищённую память (`EncryptedSharedPreferences`). Он передаётся во всех последующих запросах в заголовке `Authorization: Bearer <authToken>`.

- **Ошибки:**
  - `400 Bad Request` — `{"error": "Missing pinCode or secretToken"}`
  - `401 Unauthorized` — `{"error": "Invalid or expired pairing code"}` (PIN неверен, уже был использован или истекли 10 минут).

---

#### 3. Проверка статуса устройства: `GET /api/v1/device/status`
- **Назначение:** Проверка валидности сохранённого токена и отсутствия отзыва доступа (revoke).
- **Заголовки:** `Authorization: Bearer <authToken>`
- **Ответ при успехе (200 OK):**
```json
{
  "status": "authorized",
  "deviceId": "dev_1730309400000_k9x2pa",
  "deviceName": "Google Pixel 8 (Android)",
  "lastSyncedAt": "2026-10-30T17:25:00.000Z"
}
```
- **Ошибки:**

### 3.5 Авторизация и безопасность
1. При сопряжении Android получает уникальный токен `authToken` (64 символа hex).
2. Сервер Windows вычисляет SHA-256 хэш: `crypto.createHash('sha256').update(rawToken).digest('hex')` и сохраняет в поле `sync_devices.token_hash`.
3. При каждом запросе сервер хэширует пришедший Bearer-токен и ищет совпадение в таблице `sync_devices`.
4. Если поле `revoked_at IS NOT NULL`, сервер возвращает `403 Forbidden`. Доступ устройства аннулирован пользователем Windows.
5. Количество сопряжённых устройств не ограничено.
6. Подключение без действующего PIN / QR-кода невозможно.

### 3.8 Временные метки и разрешение конфликтов (Conflict Resolution)
В исходном коде Windows-приложения (`src/storage/repositories/syncRepository.ts:321-381`) реализован детерминированный алгоритм разрешения конфликтов:

1. **Формат времени:** Все даты (`created_at`, `updated_at`, `completed_at`, `deleted_at`) строго хранятся в формате **ISO 8601 UTC** с миллисекундами (`YYYY-MM-DDTHH:mm:ss.sssZ`).
2. **Базовый алгоритм:** **LWW (Last-Write-Wins)** на основе лексикографического сравнения строк ISO 8601: `incoming.updated_at > local.updated_at`.
   - Если версия клиента новее (`client.updated_at > server.updated_at`), сервер принимает изменения клиента.
   - Если версия сервера новее (`server.updated_at > client.updated_at`), сервер игнорирует изменение клиента в этой транзакции, и обновленная версия с сервера передается клиенту в `serverChanges`.
3. **Интеллектуальное слияние заметок (Smart Notes Merge):**
   Если обе стороны в офлайне независимо отредактировали текст заметки/описания (`notes`), сервер предотвращает потерю данных!
   Код проверки:
   ```typescript
   if (local.notes && t.notes && local.notes.trim() !== t.notes.trim() && !t.notes.includes(local.notes)) {
     mergedNotes = `${t.notes}\n\n[Версия с компьютера (${local.updated_at})]:\n${local.notes}`;
     conflictsResolved++;
   }
   ```
   В результате текст заметки с компьютера бережно дописывается вниз, предотвращая случайную потерю правок.
4. **Порядок применения пакета изменений:**
   - Сначала применяются метки физического удаления (`tombstones`).
   - Затем применяются проекты (`projects`).
   - В последнюю очередь применяются задачи (`tasks`), гарантируя наличие родительских проектов для внешних ключей.

### 3.9 Удаление и восстановление (Soft Delete & Tombstones)
В системе строго разделены два понятия:
1. **Мягкое удаление в корзину («Мусор»):**
   - У задачи устанавливается `destination = 'trash'`, `deleted_at = <ISO 8601>`, `updated_at = <ISO 8601>`.
   - У проекта устанавливается `deleted_at = <ISO 8601>`, `updated_at = <ISO 8601>`.
   - Запись **остаётся в базе данных** и синхронизируется как обычный объект с заполненным полем `deleted_at`.
   - **Связи проекта и задач не разрываются!** При перемещении проекта в мусор поле `task.project_id` остаётся нетронутым.
2. **Восстановление из корзины:**
   - Для задачи: `destination = 'inbox'`, `deleted_at = NULL`, `updated_at = <now>`.
   - Для проекта: `deleted_at = NULL`, `updated_at = <now>`. Связанные задачи проекта мгновенно снова отображаются внутри восстановленного проекта.
3. **Окончательное физическое удаление (Permanent Delete):**
   - Строка физически удаляется из таблицы: `DELETE FROM tasks WHERE id = ?`.
   - В таблицу `sync_tombstones` записывается метка: `(entity_type, entity_id, deleted_at)`.
   - При синхронизации метка `tombstone` передается мобильному клиенту, и клиент выполняет `DELETE` в своей базе данных, исключая «воскрешение» удаленных записей.

## 4. Полная логика GTD

В Windows-версии реализован классический цикл David Allen GTD:

1. **«Корзина ГТД» (`inbox`):**
   - Первичный накопитель неструктурированных мыслей и задач.
   - Задачи попадают сюда через быстрое добавление (`Ctrl+N` или кнопка «+»).
   - **Выборочный или последовательный разбор:** Пользователь может разобрать любую задачу независимо от порядка (кнопка «Разобрать» на конкретной карточке) либо запустить последовательный разбор («Разобрать по порядку»).
   - При разборе запускается конечный автомат (`GTDStateMachine`):
     - *«С этим надо что-то делать?»* -> Нет -> Выбор: «Мусор» (`trash`) или «Заметки» (`notes`).
     - *«С этим надо что-то делать?»* -> Да -> *«Мне?»* -> Нет -> Форма делегирования -> раздел `waiting_for`.
     - *«Мне?»* -> Да -> *«Сейчас?»* (в пределах недели) -> Нет -> Выбор: «Календарь» (`calendar`) или «Когда-нибудь» (`someday`).
     - *«Сейчас?»* -> Да -> *«Одношаговая?»* -> Нет -> Создание проекта с 1-м шагом (`projects`).
     - *«Одношаговая?»* -> Да -> *«Правило 2 минут»* -> Сделать сразу (таймер на 2 минуты) или перенести в `next_actions`.
2. **«Текущие действия» (`next_actions`):**
   - Конкретные ближайшие действия, готовые к исполнению. Главный рабочий экран по умолчанию при запуске.
3. **«Календарь» (`calendar`):**
   - Задачи, привязанные к конкретной дате (`scheduled_date`) и времени (`scheduled_time`).
4. **«Делегирование / Ожидание» (`waiting_for`):**
   - Задачи, порученные другим людям. Содержат имя ответственного (`delegated_to`), суть ожидания (`waiting_for`) и дату контроля (`check_date`).
5. **«Когда-нибудь потом» (`someday`):**
   - Идеи, отложенные на неопределённый срок без жестких обязательств.
6. **«Заметки» (`notes`):**
   - Справочные материалы, конспекты, инструкции. Не являются задачами (не имеют чекбоксов выполнения). Редактируются в Markdown.
7. **«Проекты» (`projects`):**
   - Комплексные цели с прогрессом выполнения шагов.
8. **«Завершённые» (`completed`):**
   - Архив выполненных задач (`status = 'completed'`). Поддерживается возврат задачи в статус активной одним кликом.
9. **«Мусор» (`trash`):**
   - Отклонённые входящие и удалённые элементы (`deleted_at IS NOT NULL` или `destination = 'trash'`).

## 5. Проекты и задачи

### 5.1 Создание проекта
- Вызов `projects:create` создаёт проект и **одновременно первый конкретный шаг** (задачу):
  1. В `projects` вставляется проект с `status = 'active'`.
  2. В `tasks` вставляется первый шаг с `project_id = project.id`, `project_order = 1`, `destination = 'inbox'` (для последующей обработки «Мне?»).
  3. В `projects.first_step_task_id` прописывается ID созданной задачи первого шага.
  4. Если проект создан из входящей задачи, исходная задача удаляется.

### 5.2 Добавление шагов в проект
- Любая задача связывается с проектом через внешнее поле `task.project_id = project.id`.
- Задачи внутри проекта могут иметь любой `destination` (например, один шаг в `next_actions`, второй в `waiting_for`, третий в `calendar`).
- Прогресс проекта рассчитывается динамически:
  $$\text{Progress} = \frac{\text{Количество задач проекта со статусом completed}}{\text{Всего задач с project\_id = project.id}} \times 100\%$$

### 5.3 Завершение и приостановка
- Статусы: `'active'`, `'completed'`, `'on_hold'`.
- При переводе проекта в `completed` фиксируется `completed_at = <ISO 8601>`.

## 6. Markdown и заметки

### 6.1 Формат хранения данных
- Исходный текст заметок хранится **исключительно в текстовом виде как стандартный Markdown** в колонке `tasks.notes` (где `destination = 'notes'`).
- Заголовок заметки хранится в `tasks.title`.
- Нет никаких кастомных бинарных структур или проприетарного JSON в базе. Android-клиент может отображать и сохранять этот же текст без промежуточных преобразований.

### 6.2 Два режима редактирования (Windows)
1. **Визуальный режим (WYSIWYG):**
   - Открывается по умолчанию при каждом открытии заметки.
   - Построен на TipTap 3 (`tiptap-markdown`).
   - Автоматически форматирует текст на лету при вводе Markdown-синтаксиса (например, ввод `**жирный** ` скрывает звёздочки и делает текст жирным, `# ` превращает строку в заголовок).
   - **Строго без панелей инструментов (No Toolbar):** Форматирование осуществляется через контекстное меню по правому клику мыши (ПКМ) либо горячие клавиши.
2. **Markdown-режим (исходный код):**
   - Моноширинный редактор сырого текста Markdown.
   - Поддерживает умное продолжение списков при нажатии Enter (`- ` или `1. `) и мягкую табуляцию (2 пробела).
3. **Переключение режимов:**
   - Кнопки переключения «Визуальный» / «Markdown» находятся в шапке редактора.
   - Текст синхронизируется через единый `content`-стейт без потери изменений.

### 6.3 Матрица поддержки Markdown

| Возможность | Поддерживается | Формат хранения в базе | Особенности реализации |
|---|---|---|---|
| **Жирный текст** | Да | `**текст**` | Парсится TipTap / CommonMark |
| **Курсив** | Да | `*текст*` | Одинарные звёздочки |
| **Зачёркивание** | Да | `~~текст~~` | Двойные тильды (GFM) |
| **Подчёркивание** | Да | `<u>текст</u>` | HTML-тег `<u>` (сохраняется в markdown) |
| **Встроенный код** | Да | `` `код` `` | Одиночные бэктики |
| **Заголовки H1–H3** | Да | `# H1`, `## H2`, `### H3` | Стандартные решётки с пробелом |
| **Цитаты** | Да | `> текст цитаты` | Символ `>` в начале строки |
| **Маркированный список** | Да | `- элемент` или `* элемент` | Символ дефиса |

## 7. Даты и временные зоны

1. **Разделение полей:**
   - `due_date` и `scheduled_date` хранятся строго в формате даты: `YYYY-MM-DD` (без времени и часового пояса).
   - `due_time` и `scheduled_time` хранятся в 24-часовом формате: `HH:mm`.
   - Временные метки системы (`created_at`, `updated_at`, `completed_at`, `deleted_at`) хранятся в полном UTC ISO 8601: `YYYY-MM-DDTHH:mm:ss.sssZ`.
2. **Смена часового пояса:**
   - Поскольку дата выполнения хранится как `YYYY-MM-DD`, смена часового пояса на устройстве не смещает дату задачи на день назад/вперёд.
3. **Определение сегодняшнего дня:**
   - Вычисляется по локальному системному времени устройства: `new Date().toISOString().split('T')[0]`.

## 10. Тестовые сценарии проверки совместимости

### Сценарий 1: Первичное сопряжение по QR-коду
- **Действие:** Windows генерирует QR-код. Android сканирует его камерой и отправляет `POST /api/v1/pair`.
- **Ожидаемый результат:** Сервер возвращает 200 OK с `authToken`. Android сохраняет токен. В Windows в списке устройств появляется Android-устройство.

### Сценарий 2: Первичное сопряжение по 6-значному PIN-коду
- **Действие:** Android отправляет `pinCode` вручную.
- **Ожидаемый результат:** Авторизация успешна. Повторный ввод этого же PIN возвращает 401 Unauthorized (одноразовый код).

### Сценарий 3: Создание задачи на Android и получение на Windows
- **Действие:** На Android создана задача `Купить молоко`. Отправлен `POST /api/v1/sync`.
- **Ожидаемый результат:** В ответе `stats.appliedTasks = 1`. На Windows задача мгновенно появляется в списке задач.

### Сценарий 4: Создание проекта с шагами на Windows и получение на Android
- **Действие:** На Windows создан проект `Ремонт кухни` с первым шагом `Замерить стены`. Выполнен запрос с Android с `lastSyncedAt`.
- **Ожидаемый результат:** В `serverChanges.projects` приходит проект, в `serverChanges.tasks` приходит шаг с `project_id = proj.id`. Связь сохранена.

### Сценарий 5: Мягкое удаление проекта в «Мусор»
- **Действие:** Проект перемещен в корзину на Windows. Выполнен `POST /api/v1/sync`.
- **Ожидаемый результат:** Проект приходит с заполненным `deleted_at`. Задачи проекта не теряют `project_id`. На Android проект перемещается в корзину.

### Сценарий 6: Восстановление проекта из корзины
- **Действие:** На Android нажат возврат проекта. Поле `deleted_at` сброшено в `null`. Отправлен sync.
- **Ожидаемый результат:** На Windows проект восстанавливается в активные со всеми своими шагами.

### Сценарий 7: Автоматическое объединение заметок при конфликте (Smart Merge)
- **Действие:** Задача имела заметку `Версия А`. Без сети Windows изменил на `Версия Компьютер`, а Android на `Версия Телефон`. Проведена синхронизация.
- **Ожидаемый результат:** Заметка на Windows и Android получает объединенный текст с сохранением обеих правок, `conflictsResolved = 1`.

### Сценарий 8: Физическое удаление (Permanent Delete) через Tombstone
- **Действие:** В корзине на Windows нажато «Удалить навсегда». Строка удалена, создан tombstone. Проведена синхронизация.
- **Ожидаемый результат:** В `serverChanges.tombstones` приходит запись. Android удаляет задачу из локальной базы Room. Задача не появляется повторно.

## 11. Что неизвестно или требует дополнительной проверки

1. **Номер порта сервера:**
   В первоначальной документации `SYNC_SPECIFICATION.md` фигурировал порт `52498`. Однако в реальном исполняемом коде `src/main/sync/syncServer.ts` (строка 12) задан порт **`52420`**. Android-разработчик должен ориентироваться на порт из QR-кода или использовать порт по умолчанию `52420`.
2. **Фоновая синхронизация на Android:**
   Windows-сервер работает только когда компьютер включён и приложение запущено. При выключенном ПК запрос синхронизации с Android будет завершаться тайм-аутом (`SocketTimeoutException`). Android-клиент должен корректно обрабатывать это состояние как штатный офлайн, не сбрасывая авторизационный токен.
3. **Размер полезной нагрузки:**
   Сервер Windows ограничивает размер JSON-тела в `50 МБ` (`src/main/sync/syncServer.ts:286`). Поскольку заметки и задачи текстовые, этого лимита достаточно для сотен тысяч записей.
